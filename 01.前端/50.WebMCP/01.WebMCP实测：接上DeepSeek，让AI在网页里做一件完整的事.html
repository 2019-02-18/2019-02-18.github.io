WebMCP 实测：接上 DeepSeek，让 AI 在网页里做一件完整的事 ​

给 AI 一句话，让它把网页上的生日邀请函改好，保留报名表；再写一段可以播放、可以导出 MIDI 的旋律。这是我最近拿 WebMCP DevTools 做的两组测试。

听起来很像常见的 AI 演示。但我更想知道中间发生了什么：模型到底调用了哪个工具？参数有没有填错？网页真的变了吗？它说“已经完成”的时候，有没有能对上的结果？

所以这次接上了真实的 DeepSeek API，把调用记录、页面截图和导出文件一起留了下来。过程中有成功，也有错误，甚至有一句看着很顺、算起来却不对的结论。

WebMCP 到底解决了什么问题？ ​

我觉得它最有价值的地方，是让网页成为 AI 可以直接操作的工作空间。

拿音乐来说，聊天框给出一串音符，离一首可以继续编辑的作品还有距离：你得把它们搬进软件，调整节奏、试听，再把修改意见告诉 AI。在这个页面里，模型读取的就是你眼前的曲谱，写入的也是同一份曲谱。你可以边听边调低伴奏，AI 接着改主旋律，最后导出 MIDI。人和 AI 操作的是同一个作品。

传统浏览器自动化也能完成不少操作，但它往往需要先找到按钮、输入框和列表，再模拟点击。WebMCP 为已经接入的页面增加了更明确的入口：music_set_song 接收完整曲谱，data_query 接收筛选条件，页面自己校验并执行。一次业务操作不必拆成几十次界面点击；按钮挪了位置，也不必因此改变工具的参数。这里说的是交互路径更直接，并不是本次测试测出了多少倍的速度提升。

它和普通后端 API 也有不同的切入点。网页里有当前选中的轨道、未保存的草稿、筛选条件、撤销历史和等待确认的方案。这些状态就在用户当前的工作现场。工具可以围绕这些状态设计，执行后立刻反馈到界面，用户看得见、改得动，也能决定什么时候继续。

这几组例子对应了三个实际收益：

你想完成的事页面提供的能力WebMCP 带来的变化
把想法变成作品读取和修改曲谱、网页区块，导出文件AI 的结果进入现有编辑流程，不停在聊天文字里
根据数据作判断筛选、聚合、返回来源行计算由页面完成，模型负责组织任务和解释，结论能回查
调整一项有后果的计划提交候选方案、展示差异、等待确认AI 可以准备修改，最终确认仍留给使用者

但它需要网站主动接入。安装插件不会让所有网站自动拥有工具，也不会让模型的判断自动变正确。写入校验、权限和人工确认仍要由应用做好。它更适合已有编辑器、数据工作台和业务系统：这些产品本来就有明确的操作，现在可以把它们开放给 Agent。

这也是我做 DevTools 的原因。网页对外声明了什么能力、模型到底调用了什么、失败发生在哪一步，需要一套能看见过程的调试工具。Playground 展示这些能力可以怎么设计，插件则帮助你在自己的页面上把它们调通。

网页先把自己能做的事说清楚 ​

WebMCP 的出发点很好理解：网页可以把某些能力明确注册成工具，告诉 Agent 这个工具叫什么、接收什么参数、执行后返回什么。比如“读取当前曲谱”“修改一个区块”“计算筛选后的金额”。

这样，模型能围绕这些具体能力完成任务，网页继续负责校验、计算和更新界面。读者也能在原来的页面上看到结果，接着手动修改。

它仍是一个在演进中的 Web 标准提案。Chrome 当前提供命令式 JavaScript API 和声明式表单 API，本地开发可以开启 WebMCP 测试开关。浏览器支持情况与 API 细节，建议以 Chrome 官方文档 为准。

对于前端开发者，一个工具大致长这样。下面是独立的最小示例，不是这次对话里的模型输出：

js
await document.modelContext.registerTool({
  name: 'calculate_meal_budget',
  description: '按人数和每人费用计算餐食预算',
  inputSchema: {
    type: 'object',
    properties: {
      guests: { type: 'integer', minimum: 1, maximum: 1000 },
      perGuest: { type: 'number', minimum: 0, maximum: 1000000 }
    },
    required: ['guests', 'perGuest']
  },
  execute: async ({ guests, perGuest }) => {
    if (!Number.isInteger(guests) || guests < 1 || guests > 1000 ||
        !Number.isFinite(perGuest) || perGuest < 0 || perGuest > 1000000) {
      throw new Error('人数或单价无效')
    }
    return { total: Math.round(guests * perGuest * 100) / 100 }
  }
})

Schema 帮模型理解参数，执行函数仍然需要校验输入。涉及业务数据时，也要在真正处理数据的地方做权限检查。命令式 API 文档里有更完整的用法。

我为什么做这个插件 ​

接入工具之后，调试问题就很具体了：注册成功没有？参数结构是什么？模型传进来的值是什么？调用失败，是模型选错工具，还是执行函数报错？

我做的 WebMCP DevTools，就是把这些东西放进浏览器侧栏。先看工具列表和参数，必要时手动执行一次，再到 AI 面板里发出任务。出了问题，可以回到执行记录看输入和返回值。

这里是扩展读取到的工具列表。测试时将扩展面板独立打开；不是画出来的界面。

另外还有执行历史、工具快照对比、测试用例和导出。它们是开发者排查问题时的辅助功能，本文重点看 AI 面板能否把任务真正做完。

本文记录的这轮测试使用本地开发版 WebMCP DevTools 2.3.2、Playground 3.0.0、Chrome for Testing 151.0.7922.34，模型是 deepseek-flash，非思考模式。模型请求实际发送到了 DeepSeek 官方 API，截图和网页交互由浏览器自动化脚本记录。

本文写于 2026 年 10 月 22 日。商店当时显示的版本仍是 2.2.0，所以文中的新版功能不能直接当作当前商店版的承诺。下面的结果也只代表这组测试页面与模型配置。

先做一张能用的邀请页 ​

网站工坊里原本就有一张基础邀请函。我给模型的要求是：

把当前网页改成“周末的生日小聚”邀请函，时间是 2026 年 10 月 31 日 14:00，地点是城市花园，主题色用暖橙色。保留可以填写称呼和人数的报名表，文案自然一点，不要夸张。先读当前版本，修改时携带版本号，最后检查预览控制台。

这次模型进行了 3 次工具调用：读取当前网站、写入修改、检查预览控制台。页面版本从 1 变成 2，标题、颜色、时间和地点都更新了。

模型写下的正文是：“没什么特别的安排，就是想和大家一起吃顿饭、聊聊天。有空的话来坐坐，一起过个生日。”

这个结果比较符合我想要的普通邀请函。更值得注意的是，它在最后主动区分了两件事：控制台没有报错，但它并没有实际填写并提交报名表。

于是测试脚本补做了这一步：填入“测试来宾”、人数 2，提交后，页面显示收到报名。之后导出了网站 ZIP，里面有 HTML、CSS 和 JavaScript。

下载本次生成的邀请网页 ZIP。

报名目前只是本地演示，不会把信息发给主办人。要拿去正式使用，还得接上自己的数据存储或提交接口。WebMCP 能调用页面已经实现的能力，不会凭空补出一个后台。

音乐终于有了完整的音符 ​

音乐页的测试，我没有让模型解释怎么写歌，而是直接要求写进当前曲谱：

写一段 8 小节、3/4 拍、108 BPM 的生日祝福旋律，C 大调，钢琴主旋律加轻柔低音伴奏，结尾落在 C 上。有短句呼应和长短音变化，不要只循环几个固定音。

最终的曲子叫《周末的小小祝福》。从页面状态核对，钢琴轨道有 27 个音符，低音轨道有 15 个，一共 42 个音符、24 拍，时长约 13.33 秒。两个声部最后分别落在 C4 和 C3，MIDI 也导出了。

中间并不顺利。模型第一次提交完整曲谱时，把休止写成了一个叫 Rest 的音高。页面不接受这个值，写入失败。后续它换了操作方式，逐轨调整，又重新提交了整曲，最终用音符之间的时间间隔表示休止。

这组任务一共调用了 11 次工具，其中 1 次失败。最后的 music_play 返回播放成功，页面也进入播放状态。音频需要先在页面启用，这是浏览器交互流程的一部分，不能靠一句“播放成功”绕过。

这次验证到的是曲谱结构、播放调用和 MIDI 导出。旋律是否好听、是否适合某个具体场合，仍然需要试听判断。我把曲谱和 MIDI 留在了素材包里，没有把这次输出包装成音乐质量评测。

下载本次生成的 MIDI，也可以保留完整曲谱 JSON继续编辑。

让数据结论能找到原始行 ​

数据页里有一份 10 条记录的支出示例，其中一条金额缺失。我让模型分析 2026 年 10 月的支出，按分类求和，并明确要求不要把缺失金额当成 0。

页面计算出的结果是：

检查项实际结果
原始记录10 条
10 月筛选命中7 条
参与金额计算6 条
因金额缺失被排除1 条
餐饮支出748 元，来自原始第 5、7 行
已计入金额合计1103 元

模型把结论保存成了页面备注，附带查询标识和当时的计算结果。之后即使修改筛选条件，也能知道这条备注是在什么条件下得到的。

这里也出现了一次错误：它尝试读取第 1 行，而工具的可读取数据行从第 2 行开始，第 1 行是表头。调用被拒绝后，它改用当前筛选条件分页读取，才拿到了正确的数据。

对我来说，这比一个漂亮的图表更有说服力。金额由页面计算，模型负责选择查询和组织解释；需要核对时，可以继续往下查到具体记录。

不过，有工具返回值，不代表模型对返回值的每句话都可靠。接下来那组测试就碰到了一个很小、也很典型的问题。

AI 提方案，页面保留确认这一步 ​

活动策划台的原计划是 12 人。我要求改为 16 人，总预算 1500 元，保留音乐和蛋糕环节，先提交候选方案，等待页面确认。

模型读取计划、计算候选方案，再提交提案。它没有直接覆盖当前计划。截图里可以看到，当前计划仍是 12 人，新方案单独列在右边。

新方案的费用是餐食 880 元、蛋糕 268 元、布置 180 元，合计 1328 元，剩余 172 元。确认按钮在网页上，模型没有替用户点击的工具。

测试脚本随后执行了页面确认点击，再向模型发出“已确认，请生成邀请网页”的后续消息。模型重新读取确认状态，生成邀请页，跳转到网站工坊，再读取新页面状态，核对日期和 16 位来宾。

跨页面之后，工具列表会变。插件需要刷新工具定义，继续调用新页面里的工具。这次链路走通了。

但模型在解释预算时说了一句“人均费用随人数上升”。实际算一下，原计划是 1108 ÷ 12，约 92.33 元；新方案是 1328 ÷ 16，正好 83 元。人均费用下降了。

总费用、剩余预算和页面数据都是对的，错的是那句解释。把计算结果、模型文字和确认动作分开保存，遇到这种问题时才有地方查。

失败也应该出现在演示里 ​

我还补了三项检查。

入门页在“准备邀请”后才注册新的导出工具。模型完成预算计算和邀请准备后，确实发现并调用了这个新工具，读到了 660 元预算以及“尚未确认”的状态。

测试实验室里，lab_add(7, 8) 返回 15；故意报错的 lab_fail 只调用了一次。模型报告了失败，没有把它改写成成功，也没有反复重试。

生态页则跑出了一个失败结果：起始是 60 株植物、20 只食草动物、8 只捕食者，最终观察到第 102 步时，植物 160，另外两个种群都归零。挑战状态为 failed，模型如实报告了失败。这里有随机过程，而且只是简化模拟，不能拿它推断现实生态；它的价值是展示 Agent 如何读取状态、推进过程和解释结果。

这次保留的 8 段对话共触发 45 次模型发起的工具调用：42 次返回成功，2 次参数错误被拒绝，另 1 次是预先安排的失败测试。这个计数不包括测试脚本额外读取状态、点击确认和检查报名表的操作，也不是一项通用成功率指标。

想自己试，可以从一个小任务开始 ​

插件项目在 GitHub，已发布版本可以从 Chrome Web Store 安装。体验本文的新功能前，请先核对实际安装版本。

本地测试时，先在 Chrome 开启 chrome://flags/#enable-webmcp-testing 并重启，再打开已经接入 WebMCP 的页面。到插件的工具列表确认能发现工具，手动执行一个简单调用，然后再配置模型、尝试自然语言任务。

这次 DeepSeek 使用 deepseek-flash。接入时顺手更新了插件里过时的默认模型名称，并显式使用非思考模式。模型名称和接口行为会变化，配置时可以对照 DeepSeek 官方说明与工具调用文档。

使用云端模型时，提示词、工具定义，以及调用过程中返回给模型的数据会发往对应服务。测试页用的是示例数据；换成自己的业务页面，就需要考虑这些返回值是否适合发送出去。

我更希望这个插件能帮助开发者把任务一步步调通：先注册一个清楚的能力，确认它能正确执行，再让模型尝试组合调用。一个可以复查、可以修改、出了错也能解释的结果，比一句笼统的“AI 已经帮你做好了”更值得留下来。

自己试一试 ​

打开 WebMCP Playground，选择音乐、网站或数据场景，再从插件的工具列表和 AI 面板开始。音乐页现在直接点击播放即可试听，音量和静音支持播放中调整，无需单独“启用声音”。首次发声仍遵守浏览器的用户交互要求。本文原始 API 实测记录对应 Playground 3.0.0；这次发布的 3.0.1 增加了上述播放体验修复。
